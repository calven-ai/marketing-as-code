# Architecture: how this repo is designed, and why

The reasoning behind the structure: what each folder owns, and the design
decisions that hold it together. What is still planned is in
[roadmap.md](roadmap.md).

## Design principles

Five rules generate almost every decision below:

1. **A file lives with its lifecycle owner.** Content outlives the project
   that produced it, so content never lives inside a project folder. This
   one rule kills duplication without an index to maintain.
2. **Machine files and human files don't mix.** `data/` is append-only CSV
   that agents diff and query. `reports/` is dated narrative that humans
   read.
3. **Agent-agnostic by standard, not by duplication.** Definitions exist
   once, in the open format the ecosystem converged on, with the thinnest
   possible shim for tools that lag.
4. **Adapters are documents where a document will do.** The task-tool
   integration is a page of conventions agents read, not a code layer
   anyone maintains.
5. **Humans decide, so agents propose diffs.** Anything that cascades moves
   through review, never through silent writes.

## Four kinds of files

Every file is context, agents, code or data. The folders are the
implementation; the four kinds are the model, defined in
[AGENTS.md](../AGENTS.md). The split matters because each kind asks a
different thing of an agent. Context is loaded before thinking, never
guessed at. Code is run instead of reimplemented. Data is treated as
evidence: queried, diffed and quoted, never invented. Agents are edited as
text, so changing what the workforce does is a reviewable diff, not a
deploy.

## The target tree

```
marketing-as-code/
├── .agents/skills/<name>/       # canonical agent & skill definitions (open standard)
├── .claude/skills/<name>        # per-skill symlinks into .agents/skills/ (Claude Code shim)
├── .mcp.json  .cursor/mcp.json  # the same MCP servers for Claude Code and Cursor, placeholders only
├── .github/                     # PR template, CODEOWNERS, check and housekeeping workflows, crons
│
├── strategy/                    # market truth: positioning, messaging, ICP/personas, competitive
├── brand/                       # voice + visual identity + reusable design assets
├── content/                     # single source of truth for every piece, one folder per piece
├── projects/                    # PM artifacts only; a campaign is a project with children
├── data/
│   ├── ontology/                # metrics, funnel, events, naming: the measurement truth
│   ├── seo/                     # keywords.csv (canonical) + snapshots/
│   ├── analytics/               # web analytics snapshots (GA4 / PostHog)
│   ├── crm/                     # pipeline, signups, email performance snapshots
│   └── accounts/                # prospect lists, ABM research, enrichment outputs
├── reports/                     # human-first outputs, incl. self-contained HTML dashboards
├── memory/                      # decision log, knowledge base, transcript pipeline
├── agents/                      # the human-readable workforce roster (index)
├── integrations/                # registry, the integration guide, the task-tool adapter
├── scripts/                     # deterministic non-AI code (OG images, pulls, sync, doctor)
├── playgrounds/                 # disposable prototypes
└── docs/                        # guides, this document, the roadmap
```

## Folder by folder

### `.agents/skills/`: the canonical agent and skill definitions

One folder per agent or skill, in the Agent Skills format: `SKILL.md` with
frontmatter, plus optional `scripts/` and `references/`. Cursor and Codex discover this location natively. There is
no format distinction between agents (recurring roles like `seo-analyst`)
and skills (procedures like `qmr`); the roster in `agents/README.md`
groups them for humans. Claude Code still reads `.claude/skills/`, so the
repo commits per-skill symlinks there, regenerated by
`scripts/sync_skills.py`. Per-skill rather than a directory symlink,
because Claude Code writes housekeeping files into that folder.

*Rejected:* visible `agents/` and `skills/` folders as canonical with
generated per-tool adapters (three locations, a permanent sync burden), and
Claude-only subagents in `.claude/agents/`.

### `strategy/`: market truth

Positioning, messaging, ICP, personas, product brief, battlecards. The
context agents load before thinking about marketing. Markdown here goes
stale without anyone noticing, so every file carries `source`,
`last_reviewed` and `owner`, and `scripts/doctor.py` lists files not
reviewed in 90 days. The alternative is a marketing context layer served
over MCP, where every agent reads the current document on every call and
these files become fallbacks flagged `source: context-layer`. The templates
mirror the documents Calven serves, heading for heading, so the switch is
a frontmatter flag ([integrations/context-layer.md](../integrations/context-layer.md)).

*Rejected:* a pull script that mirrors the context layer into dated files.
It reintroduces the copy the MCP removes.

### `brand/`: how we sound and look

Voice, visual identity, machine-readable `tokens.json`, logos and image
templates. Loaded whenever an agent produces anything an outsider sees.
The one sanctioned binary zone, because logos have no useful text form.

*Rejected:* `strategy/brand/`. Brand is an execution-time dependency,
strategy a planning-time one.

### `content/`: the single source of truth for every piece

One folder per piece, brief first, draft second, human review before
anything ships. Frontmatter (`project`, `status`, `channel`, `owner`,
`published`) is what lets an agent answer "what did we ship last quarter?"
with a grep. Email sequences, webinar assets and case studies are content
types here, not top-level folders.

### `projects/`: how the team organizes the work

Everything is a project. A campaign is a project big enough to have
children. A project folder holds only project-management artifacts: the
brief, status, working notes. Content never lives here; the brief lists
repo paths into `content/`, and each piece points back with `project:`.
When a project closes its folder is archived, and nothing of lasting value
goes with it. Tasks live in the team's task tool via
[`integrations/tasks.md`](#integrations-the-registry-and-the-task-adapter).

*Rejected:* separate `campaigns/` and `projects/` (the filing ambiguity
never ends), content inside project folders, and symlinks from projects
into content (they break on the GitHub web UI).

### `data/`: machine-first inputs

Per-domain folders, each with canonical tables at the root and dated,
immutable pulls in `snapshots/`. The naming convention
`YYYY-MM-DD-<source>-<what>.csv` is load-bearing: it is how an agent finds
the latest snapshot without an index. Everything stays CSV so it stays
diffable. No customer PII in a public copy, ever.

*Rejected:* reports inside `data/`, and one flat cross-domain snapshots
folder.

### `data/ontology/`: the measurement truth

Metrics, funnel stages, event taxonomy, naming conventions. Any agent
touching `data/` loads it first, and an unfilled file makes the agent ask
rather than assume. It lives under `data/` because its authors are
marketing ops, the same people who own the data.

*Rejected:* a top-level `ontology/`. Top-level real estate is for things
marketers browse.

### `reports/`: human-first outputs

Analyses, the quarterly review, ad-hoc reports, each dated and immutable
once delivered. Dashboards are self-contained HTML files beside the report
they support: inline CSS, a vendored chart library, a data block the agent
fills from CSV. They open from Finder with no build step and no dependence
on any one AI tool's format. The QMR composes the analyst, the
integrations, the ontology and the dashboard template: proof the
architecture composes.

*Rejected:* a `dashboards/` top-level, and React or build-step dashboards.

### `memory/`: the part that compounds

The decision log, topic files in `knowledge/`, and the transcript pipeline
(`transcripts/inbox/` in, `transcripts/processed/` out). The pipeline
splits deterministic I/O from judgment: a script or a person puts a
transcript in the inbox, and the chief-of-staff skill turns it into
decisions, tasks and proposed edits, always as a pull request. The details
are in [memory/README.md](../memory/README.md).

### `agents/`: the human-readable roster

A table of every agent and skill, what it does, which integrations it
needs, and a link to its definition. An index for humans; the loadable
truth is `.agents/skills/`.

### `integrations/`: the registry and the task adapter

The registry says what is wired. The guide,
[adding-an-integration.md](../integrations/adding-an-integration.md), is
what a coding agent follows to add a tool, by the ladder: the vendor's MCP
server first, its CLI second, a small script last. The runtime rule
decides as much as availability: MCP calls happen inside a session, so
anything scheduled in GitHub Actions runs a CLI or a script. That is why
DataForSEO appears twice. The task adapter, `tasks.md`, is a document, not
code: which tool, which IDs, how to file a task. Every task-creating skill
reads it.

*Rejected:* a connector catalogue maintained here (the maintainers cannot
keep it current, and a team's agent builds the one connector it needs in
an afternoon), and a code-level task adapter for a problem MCP already
solves.

### `scripts/`: deterministic, non-AI code

Python, standard library only. Skills call these instead of
reimplementing, and a new connector copies the closest one. The list is
in [scripts/README.md](../scripts/README.md); the script contract is in
the integration guide.

### `playgrounds/`

Disposable prototypes instead of decks. After the meeting, log the
decision and archive the prototype.

### The website: a standalone sibling repo, deliberately not in here

The story includes a CMS-less Astro website, but it lives in its own
repository. A deployable with `node_modules`, CI and deploy secrets would
intimidate exactly the marketers this template targets. Website releases
should not churn this repo's history, and strategy edits should not
trigger deploys. The repos still connect: a GitHub Action here opens a PR
against the website repo whenever a piece merges with
`status: published`. A companion website template is planned, with `docs/website.md` (planned)
describing the pattern.

## Where things run, and where the keys live

No server. Work runs where a person is typing to a coding agent, or
unattended in GitHub Actions, which opens pull requests and never merges.
The trade-off per workflow is in [operating-model.md](operating-model.md).
Keys follow one rule: OAuth remote MCPs where possible, so no key exists;
personal keys in each person's untracked `.env`; bot keys in the GitHub
environment `automation`, which only `main` may use. The agent in Actions
is treated as something the transcript it reads can talk into anything:
no shell, no network, one branch, and a gate that runs from `main`. The
full model is in [secrets.md](secrets.md).

*Rejected:* a hosted bot the team must keep alive, encrypted secrets
committed in-repo (a ceremony this audience will get wrong), and
Codespaces as the way to hand out shared keys.

## The routing design

The repo's job is to make any coding agent answer "how many people
attended event X and then signed up?" correctly, in any tool. Three
redundant mechanisms, because different tools load different things:
AGENTS.md carries the routing rule (check snapshots, pull if stale,
interpret through the ontology, answer inline) and the where-things-live
table. Folder READMEs are machine contracts stating what is authoritative
there and what to do when data is missing. And the analyst skills carry
the procedure with worked examples. The same question gets the same
treatment whether it was asked in Claude Code, Cursor or Codex.
